# Paced ROS transport experiment

This benchmark isolates ROS transport with separate publisher and subscriber processes. It does not capture a camera, run StereoForge depth, or measure GPU performance. Each scheduled tick supplies a 1280×720 `32FC1` depth image and `rgba8` image. Both publishers and subscribers use volatile, best-effort, keep-last-1 QoS, with no intra-process communication. Messages reuse preallocated buffers filled with a constant synthetic byte pattern. The first 16 bytes encode the source ID and a topic-dependent check word; the subscriber checks these bytes and the image shape and encoding. This is a representative check, not a full-frame checksum. The image header's seconds field carries the positive sequence ID, and warmup uses -1. These timestamps are identifiers, not capture times.

Publisher waits for both matching subscribers, warms up, and schedules on absolute 60 Hz monotonic deadlines. If a tick is more than one period late it records a skip instead of queueing stale work. Each scheduled ID is recorded with its target and pair start, and each publication's host wall and calling-thread CPU interval. The two intervals include clock-reading overhead; `publish` return does not imply receipt. Subscriber records each valid-size image's ID and monotonic callback time using a bounded preallocated trace and reports overflow. It spins for a bounded period after publisher completion. Do not interpret subscription counts or successful `publish` as proof of delivery.

Run in ROS Jazzy with `rclcpp`, `sensor_msgs`, Fast DDS RMW and Zenoh RMW installed; build with `cmake -S benchmarks/ros_transport -B BUILD -DCMAKE_BUILD_TYPE=Release && cmake --build BUILD`. Place the resulting `transport` binary in an empty writable output directory and execute `OUT=DIR bash benchmarks/ros_transport/run.sh`. `SECONDS_PER_ARM` defaults to 60 and `WARMUP_SECONDS` to 3. The script runs Fast DDS, default Zenoh and experimental Zenoh SHM serially. Set `ARM_ORDER` to a space-separated sequence to reorder or repeat arms; the recorded `arm-order.csv` contains the actual order. It uses a local router, loopback network, a 6 MiB SHM pool for limited memlock environments, with Zenoh tracing disabled in performance runs; set `SHM_TRACE_DIAGNOSTIC=1` only for a separate SHM diagnostic run; separate container/process/OS configuration must be reported with results. `/usr/bin/time -v` records each router as well as publisher and subscriber, and includes setup, warmup and shutdown, and subscriber CPU percentage includes its post-run wait.

Use `python benchmarks/ros_transport/summarize.py DIR/fast-pub.csv DIR/fast-sub.csv` for each arm. It reports scheduled, skipped, offered, unique received, duplicates, losses, call times and callback time relative to the start of the corresponding publish pair, assuming both processes share a monotonic clock. Inspect logs for invalid messages, overflow and SHM fallback. Segment creation alone is insufficient proof of payload transfer; match payload-sized allocations, producer segment IDs and subscriber mappings. The subscriber cannot independently verify all payload content or classify the transport used by each individual frame. One run does not establish a live system's throughput or latency; repeat, control background load and report uncertainty.

The runner starts publisher, subscriber, and router in separate process groups and terminates outstanding groups on exit, failure, SIGINT, or SIGTERM. It requires `setsid` from util-linux.
